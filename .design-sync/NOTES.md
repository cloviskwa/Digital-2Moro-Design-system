# design-sync notes — Digital 2Moro `/design-system` component library

## What this syncs

The **real** components from `src/app/(public)/design-system` — `src/components/ui/{primitives,controls,premium}`, `src/components/icons`, `src/components/motion`, `src/components/theme` — bundled as `@digital2moro/ui` (window global `D2M`). This is a Next.js app, not a packaged component library, so there is no `dist/`: the entry is a temporary barrel (`src/.design-sync-entry.ts`, inert — nothing in the app imports it, safe to delete) compiled to real `.d.ts` via a dedicated `tsc` declaration-only pass (`.design-sync/.build/tsconfig.decl.json`), not the converter's weaker synth-entry fallback.

**Styling**: this component family's real stylesheet is `src/styles/{variables,themes/dark,themes/light,typography,components}.css` (wired by `src/app/(public)/design-system/layout.tsx`) — a *separate* system from the public site's `d2m-public-tokens.css`. One component, `D2MGradientCard`, is a genuine cross-dependency: its CSS (`.d2m-gradient-*`) only exists in `d2m-public-tokens.css`. Fixed by extracting just that block (`d2m-public-tokens.css` lines ~7912–8438, the "D2M GRADIENT-SURFACE SYSTEM" section) plus its token dependencies (hardcoded dark-theme values, not aliased, to avoid pulling in that file's much larger conflicting `:root` block) into the bundle's `styles.css`. If `D2MGradientCard`'s CSS is ever moved into the design-system's own `components.css`, this extraction step can be dropped.

**Fonts**: "Rethink Sans" is self-hosted via `next/font/google` in the real app (build-time, no static `@font-face` to harvest from the app itself) — but the brand's own font kit (`Z:\...\BRANDING\Fonts\Rethink_Sans.zip`) has the real variable-font TTFs, copied into `.design-sync/.build/fonts-src/` and shipped via a real `@font-face` (`cfg.extraFonts` → `rethink-sans.css`). "IBM Plex Mono" has no such source on hand — still substituted via a live Google Fonts `@import` in `styles.css` (`[FONT_REMOTE]`, non-blocking).

**Logo**: no presentational `Logo` component existed in `ui/primitives` — the only real one (`src/components/layout/header/Logo.js`) is `next/image` + hardcoded `/images/logos/*.png` paths, which 404 in any standalone render context (design-sync preview or otherwise) and takes no props to override them. Added a real `src/components/ui/primitives/Logo.tsx` (exported via the barrel, so it's automatically in the design-sync's scope): the 4 official brand SVGs (`variant: 'stacked' | 'inline'` × `theme: 'dark' | 'light'`), sourced from `Z:\...\BRANDING\Logo\Final Logos\SVGs\Official-Digital2Moro-*` (saved as `.txt` there — real SVG content) and embedded as base64 data-URIs directly in the component, so it has zero external asset dependency in any context. Also added a "Logo" demo section to the real `/design-system` showcase page (`DesignSystemShowcase.tsx`) so this is now the actual documented pattern, not sync-only scaffolding.

## Fork

`.design-sync/overrides/dts.mjs` — the barrel entry and other `src/` files use `@/*` path aliases; `tsc`'s declaration emit doesn't rewrite these to relative specifiers, and `source-kit.mjs` (unlike `package-build.mjs`) imports `dts.mjs` directly rather than through the fork-aware `loadLib()`, so **the barrel's own top-level exports must use relative imports, not `@/` aliases** (see the comment in `src/.design-sync-entry.ts`) — the fork only fixes alias resolution for *nested* component `.d.ts` files (prop-type cross-references), not the entry itself.

## Known render warns (checked against on re-sync)

- `SectionEyebrow`, `LinkRow` — unauthored, floor card only (`[RENDER_BLANK]`, non-blocking). Authorable on any re-sync.
- `MotionNumber`, `MotionProgressBar` — render clean in the shipped grid `<Name>.html` (confirmed via `package-validate.mjs`'s render-check), but render blank in `package-capture.mjs`'s isolated single-story (`?story=`) grading capture specifically. Likely a `useInView`/IntersectionObserver timing quirk unique to that capture mode's viewport. Graded `good` on the strength of the shipped-render confirmation; re-check if a future `[RENDER_BLANK]` fires on these in `package-validate.mjs` itself (that would be a real regression, unlike the capture-mode quirk).
- Translucent-surface components (`Panel`, `Card`, `GlowCard`, `Cta` outline variant, `Alert`) render correctly but read washed-out gray in review screenshots — the generic preview-card wrapper (`lib/emit.mjs`) hardcodes a white `<body>` background, while this design system defaults to a black page and these components use semi-transparent surface tokens (`--d2m-bg-panel`, etc.) designed to sit on that black canvas. Not a component defect — same translucent value renders correctly in the real app. Not chased further (would need a converter-level change to the shared preview wrapper, out of scope for a per-repo config fix).

## Re-sync risks

- `src/.design-sync-entry.ts` is a real file living in the app's `src/` tree, committed to the `design-sync/token-system` branch. If that branch is ever merged, either keep the file (harmless, unimported) or delete it — a re-sync will recreate it if missing.
- `ImageShowcaseCard`'s preview uses inline SVG data-URIs instead of the real mock assets (`public/assets/images/mock/*.svg`) — those paths aren't part of this bundle and would 404 in the design agent's canvas. If mock assets are ever added to the bundle path, the preview could point at the real files instead.
- The gradient-system CSS extraction (see Styling above) is a byte-range `sed` cut from `d2m-public-tokens.css`. If that file is restructured, the line range in `.design-sync/.build/component-entry/gradient-system.css` (regenerated by hand, not by the converter) needs re-cutting.
- `tokensGlob`/`tokensPkg` are not set — no separate tokens package exists for this component family; tokens ship inline via `variables.css`/`themes/*.css` in the main `cssEntry`.
- **The claude.ai/design project the Aug 7 sync uploaded to (`f145ed6d-a6e0-43a3-aaa1-1c94d1a0d40c`) was deleted server-side** by the time of the 2026-08-15 re-sync (`GetProject` 404'd; no audit trail available to say how/why). `list_projects` also showed two other empty "Design System" projects already sitting there before this session's active work began, suggesting an earlier, unfinished attempt to recover from the same problem. This re-sync salvaged one empty project (`1915a148-cec4-433a-b023-0675fed37bb5`, now pinned in `config.json`) rather than creating a third. **The other empty duplicate (`5e86a7a1-b443-44b2-9f1e-aaa077c46c5c`) was left as-is** — this tool has no project-delete method; a human should remove it from the claude.ai/design UI if it's not wanted. If the pinned project ever 404s again on a future re-sync, repeat this salvage-or-create flow rather than assuming data loss is a bug in the sync process itself.
- This re-sync also authored `.design-sync/conventions.md` for the first time (wired via `readmeHeader`) — it hadn't existed since the original Aug 7 sync. Note for editors: `readmeHeader` must be set to a path relative to the *config home* (the directory containing `.design-sync/`, i.e. repo root here) — `.design-sync/conventions.md`, not `conventions.md`; the latter silently no-ops with `! readmeHeader: ... not found at the config home — skipped`.
- `ImageShowcaseCard`'s stored grade was cleared on this re-sync ("contract changed") even though neither its preview `.tsx` nor its underlying component source had changed (confirmed via `git log`/`git diff` — no commits touched it since the Aug 7 sync). Likely a `keyRecipe`/hashing-methodology difference between the skill version used on Aug 7 and the one bundled now, not a real regression. Re-graded `good` for all 3 cells from the fresh sheet. If this recurs on a future re-sync with no real source change, it's expected — just re-grade from the sheet, don't chase it as a bug.
